## The result the release needs to explain

The team built the EEG decoder, command logic, and replay evaluation. An externally pretrained robomimic BC-RNN executed the simulated lift. Two experiments asked different questions.

| Study | Question | Evidence to carry forward |
| --- | --- | --- |
| PhysioNet, 15 participants, 270 rollouts | What happens when EEG continuously enables or holds the lift policy? | The selected gate reduced REST activation from 40.1% to 27.9% and imagery coverage from 52.1% to 36.5%. Seven participants passed the utility screen. Selection and comparison used R08. |
| BCI Competition IV Dataset 1, four participants, 720 imagery episodes | Can EEG time a single start request under variable cue timing? | The accumulator produced 154 imagery-triggered retained lifts, 59 REST-triggered lifts, and 57 transition-triggered lifts, averaged across three seeds. The simple threshold yielded 129, 57.7, and 52. The timer yielded 123, 130, and 68. |

Label robot outcomes by the instructed state **at request time**. Describe the second experiment as recorded, acoustically cued imagery and simulated execution. The 240 native rollouts cover 80 possible within-slot start times on three robot seeds. Participants shared those simulated starts. ## Milestones 5–6 · Optional follow-up after release

5. **Find out why short cues were missed.** The accumulator detected 10/115 short cues and 245/605 longer ones. Long episodes offered more chances to trigger, and scoring excluded the first second after each cue. On the existing recordings, compare first-request detection over the same elapsed observation time for both groups. State the number of episodes still observable at each time. Show request latency from the spoken cue, requests during the transition mask, and missed episodes separately. If unequal time available accounts for the gap, publish that explanation with its uncertainty and close this line. If late evidence remains a plausible, measurable failure, write a one-page protocol for milestone 6. Treat analyses on these inspected recordings as exploratory.

6. **Test one improvement on independent recordings.** A concrete candidate is a one-second trailing EEG window against the released two-second window, using the same channels, decoder family, accumulator, calibration allowance, and robot contract. Advance it only if milestone 5 supports that choice. First verify that independent recordings have continuous EEG, irregular timing, usable idle labels, and adequate calibration data. Before examining test outcomes, freeze the participant split, development false-start budget, minimum worthwhile detection gain, allowable REST and transition regressions, and treatment of misses. Compare both procedures on identical participants and report achieved false-start rates. Run a robot comparison only if the candidate meets the predeclared criteria against the frozen EEG baseline. Otherwise archive the outcome. If suitable independent data are unavailable, leave a scoped proposal and record the release as complete.

## Parallel option · A larger EEG training study

The data feasibility work can start alongside the report. The earlier GPU campaign selected neural models on PhysioNet cue-window accuracy. The irregular-timing pilot fitted a classical decoder separately for each participant. Could a neural decoder trained across people and recording days detect cued requests sooner or more often at the same rate of false starts during REST? Keep the released accumulator and pretrained robot skill as references. [GPU campaign](../results/gpu_campaign_2026-11-13/summary.md) · [Training audit](../results/project_review_2026-11-18/review.md) · [Request pilot](../results/bciciv_ds1_request_pilot_2026-11-19/summary.md)

- **Check a source before renting hardware.** Start with Stieger and colleagues' public EEG cursor-control corpus, with over 600 hours across 62 people and 598 sessions. Inspect two sessions from the same person and one from another. Verify the event codes, channels, real trial boundaries and EEG available before and after each cue. Participants could deliberately rest to move the cursor down. Preserve that label separately from intertrial rest and unlabelled samples. Record which segments support pretraining and which could support a fair request-timing test. [Original dataset paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC8016873/) · [Original experimental protocol](https://pmc.ncbi.nlm.nih.gov/articles/PMC9305984/)
- **Freeze an independent test.** Identify compatible recordings with irregular cue timing and labelled idle periods, reserve participants or later sessions according to the intended claim, and check for recording overlap with pretraining. The four Berlin participants already informed this proposal. Use their data for development or historical comparison. Define the target calibration allowance, episode detection, cue-to-request delay, achieved REST false-start rate and transition accounting before inspecting new test outcomes. Include a timer control.
- **Measure what scaling buys.** Train one neural decoder that only uses past EEG. Compare the same architecture with and without source pretraining and the released classical method, giving each the same target calibration data. Use nested subsets of source people or sessions to see whether additional data help. Profile a single H100 on the real input pipeline, then use multiple GPUs for independent data scales, splits or seeds when useful. Compare data scales on development and evaluate one locked choice on the reserved test set. Only then replay the successful candidate against the original controller on matched robot starts.
- **Decide with evidence.** Proceed to full training when the source audit and test split support the question and a small run demonstrates working ingestion, causal predictions and measurable throughput. If the source is suitable only for pretraining, secure an appropriate timing evaluation separately. If scaling yields no gain at the specified false-start rate, report that result and retain the simpler controller.

## How to keep working across sessions

- **On entry**, read this roadmap, the latest STATUS entry, and the current branch and working-tree state. Start at the first incomplete milestone. If its deliverable already exists, test its completion criterion before creating anything.
- **During work**, use the saved source records and existing scripts. Keep changes for one deliverable together. Write generated files outside frozen evidence folders. Continue independent work if a missing dataset or runtime blocks one route.
- **At each milestone**, record what changed, the artifact path, the verification command and result, and one concrete next action in STATUS. Commit only the intended files, push to the shared project branch under the existing project workflow, and verify the remote revision. Milestones may span sessions or share a session.
- **When milestones 1–4 pass**, report the release commit and link the PDF. Stop the release work there. The follow-up has its own evidence requirements and can end with a negative result. The closeout runs on CPU. Any later paid compute or new data collection needs a defined experiment and resource budget.
